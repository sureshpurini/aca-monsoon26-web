Five Stages, One Datapath

Pipelining does not make any single instruction faster. It cuts one datapath in four places so that five instructions can be inside it at once. Every stall, every forward and every flush that follows is a consequence of that one decision — and each one you can point at on the same picture.

ACT 1

Cut the datapath

Here is the RV32I datapath from Lecture 5 — the one Drum walks end to end for every instruction. Drum executes one instruction at a time, so at any moment four of these five regions are doing nothing at all. That idleness is the entire motive for what follows.

Now cut it. Pipeline registers are the cuts: latches that hold what one region produced so the next region can use it in the following cycle, while the first region starts on something new. Nothing about the logic changes.

Datapath 5 regions · 0 cuts

Simplified: immediate generation and branch-target computation are left out, and decode stands in for the whole control path. Nothing in this lecture depends on them, and each sits inside a region already drawn.

Clock period is set by the slowest stage, not the sum of all five. That is where the throughput comes from — and why an unbalanced pipeline (one stage much slower than the rest) wastes most of the benefit.
ACT 2

The staircase, one cycle at a time

Five independent instructions — no instruction needs anything an earlier one produces. Step through and watch the pipeline fill, reach steady state, then drain. Count how many cycles pass before the first instruction finishes, and how many between finishes after that.

Each instruction still takes 5 cycles from IF to WB — latency did not improve, it got slightly worse. What improved is that one instruction finishes every cycle once the pipe is full. Latency down, throughput up: that is the trade.
ACT 3

When one instruction needs another's result

Now make the second instruction depend on the first. add writes x5; sub reads it. The write happens in WB. The read happens in ID. Step it and find the cycle where that goes wrong.

The stall is correct and it is expensive — two cycles on every dependent pair, and dependent pairs are the common case in real code. But look again at the naive trace: at the end of cycle 3 the answer already exists. It is sitting in the EX/MEM pipeline register. It just isn't in the register file yet.

Forwarding reads the value from the pipeline register that holds it rather than waiting for the register file. Flip the switch above and the bubbles vanish.

How the value actually gets back

Each ALU operand is chosen by a three-input mux. A forwarding unit compares the registers this instruction is reading against what the two instructions ahead of it are about to write, and drives the selects.

ID/EX.rs1, ID/EX.rs2
The two registers the instruction now in EX is reading. Note these are register numbers — the unit compares names, not values.
EX/MEM.rd
The register the instruction one ahead is about to write. Its result is already computed and sitting in the EX/MEM pipeline register.
MEM/WB.rd
The register the instruction two ahead is about to write. Its value has reached MEM/WB but has still not been written back.
ForwardA, ForwardB
The two select signals this unit produces, one per operand — the values in the table above.

Read together: the value I need was produced by an instruction still in the pipe, so take it from wherever it currently sits rather than waiting for the register file. If both the one-ahead and two-ahead instructions write the same register, EX/MEM wins — it is the more recent value, and taking the older one would silently compute the wrong answer.

The one case forwarding cannot save

A load produces its value at the end of MEM. A dependent instruction needs it at the start of its EX. Step this one and watch those two moments miss each other.

Forwarding cannot travel backwards in time. One bubble is unavoidable — so the hardware gives up and asks the compiler to fill the slot by reordering. That hand-off is where Lecture 11 begins.

How the hardware knows to stall

Forwarding has muxes and a unit driving them. The stall needs the same account — a bubble should not simply appear. One comparison decides it, and three signals carry it out.

One piece of notation first. ID/EX.MemRead means the field called MemRead, stored in the ID/EX pipeline register — the yellow bar between ID and EX. A pipeline register carries not just an instruction's operands but its decoded control signals, so naming a value this way says both what it is and where it physically sits this cycle.

ID/EX.MemRead
A single control bit: 1 only for a load. It is the whole reason this unit exists — an ALU result can be forwarded from EX, but a loaded value does not exist until the end of MEM, one cycle too late. So the detector fires for loads and nothing else.
ID/EX.rd
The register that load is going to write.
IF/ID.rs1, IF/ID.rs2
The two registers the next instruction wants to read — it is still sitting in IF/ID being decoded while the load is in EX.

Read together: the instruction in EX is a load, and the one right behind it wants the register that load is about to produce. Catching it here — one cycle before the collision — is the last moment the PC can still be frozen in time.

ACT 4

Fetching before you know

A branch decides where to fetch next — but it does not decide until EX. By then the pipeline has already fetched the two instructions sitting after it. Step through and watch them die.

The cost is the number of stages between fetch and the resolution point. Resolve later, lose more. Deeper pipelines make this worse, which is precisely why branch prediction (Lecture 10) matters more the deeper you go.
